# 项目经验总结

> 基于 LangGraph + FastAPI + Vue 3 的交互式多 Agent 小说创作系统

---

## 一、架构决策与取舍

### 1. 自研 Supervisor 而非 LangGraph 官方 create_supervisor

**决策**：没有使用 `langgraph.prebuilt.create_supervisor`，而是自己写了一个轻量的解析+路由逻辑。

**原因**：
- 避免每轮都调 LLM 来解析用户输入（成本高、延迟大）
- 自研路由支持**多级降级策略**：精确匹配 → 正则规则 → LLM 兜底，大部分情况零成本解决
- 路由逻辑更清晰，便于调试和维护

**心得**：框架提供的能力未必适合你的场景。当"通用"带来的成本 > 收益时，自研一个简单的版本反而更可控。

### 2. 异步 + 同步混用的代价

系统中大量同步调用（`rag_tool.py` 的 `requests.post`、`session_store.py` 的 `sqlite3` 标准库）被直接用在 async 节点里，会阻塞事件循环。

**后果**：多会话并发时，一个会话的同步阻塞会拖慢其他会话。

**当时没改的原因**：项目初期以单用户为主，追求开发速度。如果有并发需求，需要：
- Embedding/Rerank 调用改用 `httpx.AsyncClient`
- 数据库操作统一用 `aiosqlite`
- 搜索工具的 `_run_async` 开线程方案也要优化

### 3. 单文件 SQLite 的取舍

checkpointer、会话元数据、长期记忆全在同一个 `novel.db`。

**好处**：部署简单，无需额外数据库服务，一个文件搞定所有持久化。
**隐患**：生产环境单文件是瓶颈，checkpointer 的频繁写入会拖慢元数据读取。好在 checkpointer 是 LangGraph 自管的，耦合度低，未来可以拆成独立库（PostgreSQL 分支）。

## 二、技术难点与解决

### 1. SSE 流式传输的 JSON 序列化问题

**问题**：`graph.astream_events` 返回的事件中混入了 `Command`、`interrupt` payload 等不可 JSON 序列化的对象，导致 `StreamingResponse` 报 `TypeError`。

**解决**：在 `streaming.py` 中实现 `_json_safe()` 递归转换函数，遇到不可序列化的对象做类型判断和字符串化兜底。

**关键代码（`streaming.py`）**：

```python
def _json_safe(obj):
    if isinstance(obj, dict):
        return {k: _json_safe(v) for k, v in obj.items()}
    elif isinstance(obj, list):
        return [_json_safe(v) for v in obj]
    elif isinstance(obj, (Command, )) or not _is_jsonable(obj):
        return str(obj)
    return obj
```

### 2. LLM 输出 JSON 解析容错

**问题**：LLM 生成的 JSON 经常不标准（有多余的 Markdown 代码块、BOM 头、尾随逗号等），直接 `json.loads` 会抛异常，导致整轮剧情中断。

**解决**：用正则 `\{[\s\S]*\}` 提取首个 JSON 块，再 `json.loads`；解析失败时字段回退为空值，保证节点不崩溃。

**关键代码（`writer.py`）**：

```python
import re
match = re.search(r"\{[\s\S]*\}", response)
if match:
    try:
        data = json.loads(match.group())
    except json.JSONDecodeError:
        data = {}
else:
    data = {}
segment = data.get("segment", "")
options = data.get("options", [])
memory_updates = data.get("memory_updates", {})
```

这是一种**防御性编程**思维：LLM 的输出不可靠，上下游都要做容错，而不是指望 LLM 每次都输出标准 JSON。

### 3. LangGraph interrupt 的暂停恢复机制

**问题**：`interrupt()` 在剧情生成后暂停图，等待用户选择。但用户的选择（如选项 A）需要传回给恢复的图，且恢复后 supervisor 要能正确识别用户意图。

**解决**：两段式设计——
1. `supervisor_node` 在 `awaiting_user=True` 时调用 `interrupt()` 暂停
2. 前端通过 `Command(resume=user_input)` 恢复图
3. supervisor 恢复后解析输入（走多级降级策略），决定下一步路由

**心得**：`Command(resume=...)` 是 LangGraph 的官方中断恢复机制，但参数的解析逻辑需要自己设计。如果解析失败，图会进入死循环或走错路由，所以多级降级策略很重要。

### 4. Critic 防死循环机制

**问题**：审查节点如果一直不满意，会反复打回重写，形成无限循环。

**解决**：动态阈值——`effective_threshold = max(PASS_THRESHOLD - iteration_count, 1)`，阈值随迭代次数递减，越审越宽松。达到 `max_internal_iterations` 时跳过 `interrupt` 直接放行。

**心得**：这种"阈值递减 + 硬上限"的组合是一种常见的防死循环模式，在 AI 驱动的自动校验场景中很实用。

### 5. 从文件读取编码混乱

**问题**：`KnowledgeBaseLoader` 在读取 `.txt` 等文件时，我们没有指定 `encoding` 参数，导致在使用 `TextLoader` 读取文件时，如果文件编码不是 `utf-8`，就会报错。

同时，在 `server.py` 中的文件上传接口里，我们假设用户上传的都是 `utf-8` 编码的文本文件，但中文 Windows 用户默认保存的是 `GBK` 编码。这会导致 `TextLoader` 解析失败。

**解决**：在 `document_util.py` 的 `load_documents` 函数中，对文本文件（`txt, md, csv`）指定 `encoding="utf-8"`。在 `server.py` 的上传接口中，加入 `_normalize_text_bytes` 函数，在保存文件之前先尝试 `utf-8` 解码，失败则按 `GBK` 解码再重新编码为 `utf-8`。

**关键代码（`server.py`）**：

```python
def _normalize_text_bytes(content: bytes) -> bytes:
    try:
        content.decode("utf-8")
        return content  # 本来就是 UTF-8，原样返回
    except UnicodeDecodeError:
        try:
            return content.decode("gbk").encode("utf-8")
        except UnicodeDecodeError:
            return content  # 两种编码都解不了，原样返回，交给 Loader 去报错
```

**心得**：跨平台应用一定要考虑文件编码差异，Windows 的 `GBK` 编码是个常见坑，如果不做兼容处理，界面会报错，用户无法正常上传文件。

## 三、Docker 部署经验

### 1. Docker Hub 镜像拉取失败

**问题**：国内网络直接拉取 Docker Hub 镜像超时。

**解决**：配置 `daemon.json` 使用加速器镜像源（如 `docker.m.daocloud.io`）。

**配置文件（`daemon.json`）**：

```json
{
  "registry-mirrors": ["https://docker.m.daocloud.io"]
}
```

### 2. Neo4j APOC 配置的坑

**问题**：Neo4j v5+ 严格校验配置文件，`apoc.` 开头的配置**必须**放在独立的 `apoc.conf` 文件中，不能写在 `neo4j.conf` 中。写错会导致容器无限重启（`Restarting (1)` 循环）。

**解决**：
1. 先用 `docker stop neo4j` 停住容器，阻止不断重启
2. 用 `docker cp` 把容器内的 `neo4j.conf` 拷到宿主机编辑
3. 移除 `neo4j.conf` 中的 APOC 配置块
4. 新建 `apoc.conf` 文件，把 APOC 配置放进去
5. 用 `docker cp` 拷回容器
6. 用 `docker start neo4j` 启动

**注意**：`--volumes-from` 只共享挂载卷，访问不到容器的可写层，所以配置文件修改必须用 `docker cp` 方式。

### 3. Neo4j 数据持久化

**问题**：容器删除后数据丢失。

**解决**：启动时挂载三个卷目录：

```powershell
docker run ... ^
  -v D:/neo4j/data:/data ^
  -v D:/neo4j/logs:/logs ^
  -v D:/neo4j/plugins:/plugins ^
  neo4j:2025.01-enterprise
```

### 4. Chroma 和 Redis 的加速器问题

**问题**：Chroma 和 Redis 同样需要从 Docker Hub 拉取镜像。

**解决**：统一使用 `docker.m.daocloud.io` 加速器前缀拉取镜像，加速器会自动拉取官方镜像并缓存到国内节点。

## 四、RAG 知识库实践

### 1. 向量检索 + Reranker 双阶段检索

**设计**：先向量检索（ChromaDB，`k=20`）粗召回，再用 Reranker（SiliconFlow `bge-reranker`）精排保留 `top_k=5`。

**优点**：向量检索速度快但精度不够，Reranker 精度高但计算量大。双阶段结合，兼顾速度和精度。

**成本**：每次 `retrieve` 调用 = 1 次 Embedding + 1 次 Rerank API 调用。

### 2. 进程内 TTL 缓存

**设计**：在 `rag_tool.py` 中实现 `_TTLCache`，缓存检索结果（默认 300s，容量 128 条 LRU）。

**效果**：创作过程中，短期内对同一主题的多次检索命中缓存，减少重复 API 调用和等待时间。

### 3. 上传文件参考的完整链路

**补全历程**：底层能力（`document_util.py` 解析、`rag_tool.py` 检索）原本就有，但缺了用户上传入口。

**补全内容**：
- 后端：`POST /api/knowledge/upload` 和 `GET /api/knowledge/files`
- 前端：`client.js` 的 `uploadKnowledgeFile` 和 `App.vue` 的上传交互区

**完整链路**：

```
用户上传文件 → 后端保存到 knowledge_base/ → 解析分割 → 入库 Chroma 向量库
→ writer agent 创作时 retrieve_for_writing → Reranker 精排 → 注入 Prompt → LLM 生成剧情
```

## 五、前端开发经验

### 1. SSE 打字机效果

**设计**：前端通过 `EventSource` 接收 SSE 流，`node_end` 事件拿到完整正文后启动打字机定时器逐步渲染，`token` 事件不做逐字渲染（避免频繁 DOM 更新），只更新时间戳和节点状态。

**关键代码（`App.vue`）**：

```javascript
function typeWriter(index, fullText) {
  // 步长 = 字数 / (总时长 / 16ms)
  const step = Math.max(1, Math.ceil(fullText.length / (total / 16)))
  typeTimer = setInterval(() => {
    msg.text += fullText.slice(i, i + step)
    i += step
  }, 16)
}
```

### 2. 深色玻璃态 UI

**设计**：整体 UI 采用深色背景 + 毛玻璃效果（`backdrop-filter: blur()`）+ 渐变紫色系。这种风格的好处是强调沉浸感，适合创作类应用。

**技术点**：`backdrop-filter: blur(16px)` + 半透明背景 `rgba(30, 41, 59, 0.6)` 实现毛玻璃。

## 六、数据库设计经验

### 1. 三表同库

| 表 | 用途 | 框架 |
|------|------|------|
| `checkpointer` 表 | LangGraph 断点续跑 | 框架自管 |
| `session_metas` 表 | 会话元数据（标题/阶段/预览） | `session_store.py` |
| `long_term_memories` 表 | 已完成会话长期记忆（续写用） | `long_term_memory.py` |

**好处**：部署简单，一个 SQLite 文件搞定所有持久化。
**问题**：`session_store.py` 使用同步 `sqlite3`，在异步服务中阻塞事件循环。

### 2. 长期记忆持久化策略

**设计**：会话完成（`phase == done`）时，将世界观、角色、规则、前情段落、记忆状态、全部保存到 `long_term_memories` 表。

**续写流程**：读取长期记忆 → 恢复世界观/角色/规则 → 保留前情片段 → 重置交互状态 → 以 `story_progressing` 阶段启动新会话。

## 七、测试与调试经验

### 1. 节点级测试

**问题**：系统有 5 个 Agent 节点和一个复杂的图编排，单节点出问题很难定位。

**做法**：每个节点都是纯函数（输入 `NovelState`，输出部分更新），可以用单元测试独立验证。

### 2. 命令行模式调试

**做法**：`src/app.py` 提供纯终端交互入口，无需启动前端即可测试完整流程。这在调试后端逻辑时比看前端 SSE 流更高效。

### 3. 日志分级

**做法**：每个 Agent 节点和工具模块都有独立的 `setup_logger`，日志输出到 `src/logs/` 目录。通过 `LOG_LEVEL` 环境变量控制详细程度，生产环境用 `INFO`，调试用 `DEBUG`。

## 八、项目结构反思

### 1. 历史遗留的"镜像目录"

项目根目录下存在 `tools/` 和 `utils/` 的空壳目录，而实际代码在 `src/tools/` 和 `src/utils/`。这是迁移过程中留下的，应该清理但优先级不高。

### 2. exchange_rag_agent/ 目录

这是 RAG 能力的参考实现，`src/tools/rag_tool.py` 和 `document_util.py` 参考了它。作为独立模块保留，可作为备选方案测试。

### 3. 配置文件的优先级

**设计**：`configs/settings.yaml` 提供默认值，`configs/.env` 环境变量覆盖。

**问题**：`.env` 文件路径分散，`rag_tool.py` 和 `search_tool.py` 各自又 `load_dotenv(configs/.env)`，存在重复加载。已统一由 `config.py` 集中管理。

---

## 九、总结：哪些地方可以做得更好

1. **异步化不彻底**：`session_store.py`、`rag_tool.py`、`search_tool.py` 都有同步阻塞调用，在 async 服务中会影响并发性能
2. **缺少正式测试**：项目没有单元测试和集成测试，全靠手动验证
3. **配置管理混乱**：同一个 `.env` 被多个模块重复加载，`OPENAI_API_KEY` 和 `EMBEDDING_API_KEY` 是同一个值但分开配置
4. **没有用户认证**：当前是单用户系统，没有登录/权限管理
5. **前端缺少错误恢复**：SSE 连接断开后没有自动重连机制，需要用户手动刷新

这些都是在项目初期为了快速迭代做的取舍，如果后续有更多用户或更复杂的场景，值得逐一优化。
